# 並列実装Issueの分割案

状態: 2026-10-03、Q21までを反映した最終確認用。実装32件と全体追跡1件の起票本文を`docs/issues/`に作成済み。以下のIDは計画用であり、GitHub Issue番号ではない。

仕様の正本は[設計書](../md-readable_design.md)。ここでは担当範囲、先に必要な契約、検証する結果をまとめる。すべての必須機能を追跡し、段階分けを機能の削除と解釈しない。

## 契約と共有ファイル

最初のIssueで、文書構造、原文範囲、表示範囲、SourceMap、NavigationSnapshot、Session、providerの入出力と最小fixtureを確定する。位置は0-based行・UTF-8 byte列・半開区間とし、表示セル幅と区別する。本文の変更世代を渡し、古い座標や非同期結果を適用しない。

`lua/md-readable/init.lua`、設定、型定義、コマンド登録、README、help、共通テスト設定は統合担当が管理する。機能担当は自分のモジュールと専用テスト・fixtureを編集し、接続に必要な設定・コマンド・依存をIssueで統合担当へ引き継ぐ。各ブランチは独立worktreeで実装する。

同じ表を表示・コピー・整形で別々に解析しない。文書構造の共通解析結果を使い、装飾後の文字列から原文を再構築しない。参照プラグインを必須依存にせず、本体内に機能を持つ。

I27の統合担当は最後まで待機せず、I00完了後から接続を順次進める。機能担当と共有ファイルを同時編集しない。各Issueはモジュールの実装と検証までを担当し、I27が公開コマンド・configへの接続を担当する。I27の完了は全機能の結合確認後とする。

## 起票時に各Issueへ含める内容

目的・対象範囲、対象外または別Issueの範囲、具体的な入力と期待結果、依存Issueへのリンク、担当ファイル、利用する共通契約、必要なfixtureと検証手順、共有接続部分への引き継ぎを記載する。親の追跡Issueから全機能の対応先と進捗を確認できるようにする。

## 3エージェントでの進行例

I00を先に完了し、Aは文書解析・表示、BはSourceMap・同期、Cはナビゲーション・設定解析を担当する。契約とfixtureが揃ったところから独立したSSGアダプターやFocus・表・画像へ担当を移す。担当は固定の役職ではなく、その時点で着手可能なIssueを選ぶ単位とする。

統合担当は共有ファイルへの接続とレビューを管理する。機能担当のブランチで共通契約を独断で変更しない。先行Issueが未完了の間も契約fixtureによる実装は可能だが、モックだけで結合完了と報告しない。
